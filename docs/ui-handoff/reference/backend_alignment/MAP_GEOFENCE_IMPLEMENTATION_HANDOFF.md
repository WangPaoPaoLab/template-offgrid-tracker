# 地图与电子围栏：Meshtastic 参考及 App 实施交接

更新：2026-11-14。状态：需求已记录、参考研究已完成；真实地图与可靠围栏闭环待实现和真机验收。本文不表示已修改原生 App、SDK、固件或生产云端。

## 1. 用户原始需求与页面归属

- 用户要求项圈产品内部具备地图和电子围栏，并明确提出“你去看meshtastic的地图和电子围栏功能，参考一下”。对应用户需求基线 R08–R10。
- 根导航仍然只有“设备 / 我的”。路径：设备 → 项圈产品 → 网关 → 项圈 / 地图 / 围栏。地图不成为首页；聊天仍从独立产品卡片进入。
- 用户在深圳使用原 App，却默认显示斯德哥尔摩；点击下载一直排队 / 0%，开关 VPN 都没有改善。这两个问题需分别修复与验收，不能用网页预览代替修复。

## 3. 借鉴 Meshtastic 的具体做法

依据固定 Android 源码提交 `bc82f95329fcc6aee4b5f32ee7ee520ea7e14ee2`，不泛指用户安装的任意版本，也不混用 Android / Apple / Desktop 能力。

| 参考点 | 在 KEEPTEEN 中的落点 |
| --- | --- |
| 节点标记可点选、位置重叠时聚合 | 地图点项圈出现简洁摘要，继续进入该项圈详情；大量同位置节点不互相遮挡 |
| 我的定位、节点视野、底图 / 图层分开操作 | 明确“我的位置 / 查看全部项圈 / 图层 / 离线地图”，手机和项圈位置不是同一个点 |
| 圆形半径与地图画矩形的简单创建方式 | 默认圆形，其他形状作为可选工具；保留现有后端支持的椭圆、多边形，不宣称是从 Meshtastic 直接获得这些形状 |
| 进入、离开提醒分别选择 | 创建流程：画区域 → 选项圈 → 选进入 / 离开 → 命名 → 保存并同步到明确执行端 |
| 首次收到位置只建立状态 | 新围栏 / 新项圈的首次有效位置不直接产生越界事件；后续区域状态变化才形成事件 |
| 提醒对象与订阅范围明确 | KEEPTEEN 使用当前网关下明确的项圈 ID 范围及授权；不是把其他客户端共享的区域一律变成自己的告警 |

Meshtastic 所查实现是在 App 中依据收到的其他节点位置作区域计算并发本地通知，不是手机系统自身位置的地理围栏，也不能证明本项目网关在手机断开后仍可监测。所查代码的首次基线、坐标有效性与有序处理值得参考；不能因此声称已经具备完整的定位精度处理、时间乱序处理或漂移抑制。

## 4. App、SDK、云端与固件分别做什么

| 工作 | 主要责任方 | 交付结果 |
| --- | --- | --- |
| 初始视野与位置权限 | App | 有有效项圈先适配项圈视野；否则按许可定位手机；均不可用时给出位置 / 区域选择引导，不默认显示斯德哥尔摩 |
| 节点与手机位置适配 | App + SDK | 保留来源、采集与接收时间、有效性和坐标系；精度未上报时不伪造精度圈 |
| 下载任务桥接 | SDK / 原生地图 | 区域、版本、大小、排队、传输、校验安装、失败原因；真实取消、重试、移除与空间不足恢复 |
| 地图与围栏绘制 | App | 标记、聚合、选中摘要、图层、区域编辑；新鲜位置和历史位置可区分 |
| 规则与告警适配 | App + 云端 | 创建 / 编辑 / 删除、范围、启停、版本、权限、同步结果与告警确认，不编造不存在的 REST API |
| 可靠进入 / 离开事件 | 所选实际执行端 | 首次基线、有效位置筛选、时间顺序、漂移处理、去重及失联状态 |
| 网关独立离线围栏（如要发布） | 固件 + SDK + App | 确认硬件存储与几何判断、规则下发 / 读回、版本和结果、断手机断云的实测；协议有字段不代表此项已完成 |

近期建议先修复现有地图链路和错误处理，评估结果再决定是否更换引擎。没有在此交接中决定更换为 MapLibre、高德或任何其他服务。

## 5. 待确认的数据契约

以下是设计需要的信息，不表示当前接口已提供全部字段：

- 位置：项圈稳定 ID、所属 / 观测网关、经纬度、坐标系、采集时间、接收时间、有效性，以及实际提供时的精度。内部原始位置与围栏几何使用一致坐标系，底图转换在显示层成对处理。
- 区域与规则：区域 ID、形状和几何、明确项圈 ID 列表、进入 / 离开提醒。启停、revision、网关范围、执行端等当前缺失项需定义新增契约。
- 规则状态：本机草稿、待同步、同步失败、已在明确执行端启用、已暂停。保存不直接置为监测中。
- 告警：稳定事件 ID、项圈、区域、进入 / 离开、发生时间与位置、有效 / 解除、确认权限及确认结果。界面不能只改数组就宣称云端已确认。
- 下载任务：地区资源 ID、地图数据版本、预计 / 已下载大小、任务阶段、错误码、可否重试、安装结果与本地实际文件。排队不直接当作已开始传输。

当前云端空 deviceIds 表示整个 Profile 的范围；不得把它误当当前网关。网页目前将“当前网关现有项圈”保存为明确 ID 快照，新项圈不会自动加入旧规则；如需动态全体范围，必须另行约定。

## 6. 原版“斯德哥尔摩 / 0%”问题的已有证据

- 默认中心写死为 59.3293 / 18.0686；这不是深圳位置被坐标转换到欧洲。
- SDK 在底层请求真正开始前即可发 Queued 事件；0% 不能证明网络请求已经发出。
- 现有桥接对部分原生状态、错误码、取消重试管理存在缺口；需要手机当次日志和实际资源 ID，而不是只切换 VPN。
- 此前仅在开发电脑做过元数据与地图文件 HEAD 检查，未下载正文、未在用户手机复现；不能作为手机端下载可用的结论。

完整调用链、版本、此前网络检查和坐标 / 服务费用说明见 [原版地图与围栏核查](MAP_AND_GEOFENCE_REVIEW.md)。

## 7. 发布前逐项验收

1. 深圳首次打开不固定在斯德哥尔摩；拒绝位置权限、无 GPS、无节点都有可理解的入口。
2. 手机位置与远端项圈分开，最近上报不能使过期 GPS 被显示成实时位置。
3. 已下载区域在无互联网、App 重启后可真实显示，未覆盖区域明确提示。
4. 下载排队、0%、超时、取消、重试、失败和空间不足均可恢复；完成意味着真实数据包校验安装成功。
5. 中国与海外实地点位、切换底图、节点标记和围栏轮廓的坐标一致，不反复加偏。
6. 首次有效位置只建立基线；后续内 → 外、外 → 内各形成一次对应事件。
7. 边界漂移按定位精度与上报周期设计确认策略，通过实测后确定参数；不能固定一个未经验证的通用缓冲距离。
8. 缺失、非法、过期及乱序位置不会造成假越界；失联独立呈现，不能当作围栏内安全。
9. 多网关规则、节点和告警不串组；新加入项圈的范围行为与规则约定一致。
10. 无权限、保存失败、同步失败和告警确认失败不会被页面显示成成功。
11. 云端监测断网时明确暂停 / 不可确认；手机后台和网关离线运行分别实测，不互相冒充。
12. 以实际 App / SDK / 固件版本留真机记录；网页截图或模拟计时不作为以上项目通过的证据。
